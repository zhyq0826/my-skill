# 服务端国际化治理

## 找到现有事实来源

先查目标项目的语言注册、资源加载、翻译入口、错误码映射及领域依赖方向。复用现有架构，不再建立并行语言列表、加载器或翻译键副本。

## 语言取决于接收者

- 当前请求响应：使用请求链路解析并传递的语言，检查中间件确实注入，且下游调用按契约传播。
- 指定用户通知或异步消息：优先依据接收用户的语言偏好。即使存在 context，也不能把发起人的语言当成接收人的语言。
- 无请求语言也无用户偏好：使用明确配置的默认语言或地区回退策略。

区分任务 context 与语言上下文；检查语言码归一化、未知语言及资源缺失时的回退链。不要仅按“函数是否有 ctx”机械选择翻译方式。

## 翻译键与分层

静态键使用项目已有的常量、类型化键或生成目录作为唯一来源。动态条件优先映射到完整合法键，避免任意拼接。数据库驱动的动态键按其 schema 和资源目录校验，不强行转成静态常量。

先核对资源中真实存在的键及同义文案，不凭注释猜测。插值参数、复数规则和格式约定要与调用方一致。新增语言按既定完整性与发布策略补齐资源，缺失项不能无意地长期依赖回退。

基础翻译层不反向依赖具体业务模型；业务枚举到键的映射放业务层或合适的共享模块。需要用户语言时传入语言值或窄接口，避免引入整个用户模型。服务内部保持稳定错误语义，通常在用户响应边界翻译；不要强制所有项目都在同名网关翻译。

## 验证

选择覆盖本次改动的请求语言、接收者语言、默认回退、缺键及插值测试；检查语言注册与资源同步、依赖环及实际下游语言传播。只修改相关链路，遗留路径不自动扩展为全仓重构。
