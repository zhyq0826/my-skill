# PRD 工程化

## 从业务需求到可实现规格

先读取需求和相关代码、接口契约、存储及项目约定。区分现有能力、拟新增能力和待验证假设；不能把产品设想写成代码现状。仅澄清会改变范围或正确性的阻塞问题，其余合理假设明确记录。

工程规格重点说明用户目标、主要流程、实体与状态机、权限、异常边界和验收行为。实体字段写清业务含义、单位、可选性、默认值与快照语义。适合复杂需求时参考 [工程规格模板](templates/engineering-prd.md)，小任务可合并为一份短文档，不强制画图或固定章节数。

## 数据生命周期账本

分开描述长期业务事实、短期运行态、调度元信息和统计值。对相关数据明确事实源、访问模式、保留期限、恢复路径和淘汰责任。

业务有效期、扫描窗口、队列成员清理和缓存 TTL 不能混成一个“过期时间”。删除运行态后，系统是否还需要恢复历史事实；缓存失效后从哪里重建；这些应在进入实现前说明。

## 开发计划

使用 [开发计划模板](templates/development-plan.md) 按需组织。先确定关键契约，再按能实际演示的端到端行为拆成垂直切片，每项任务应可审查，有清晰范围、依赖和验收方式。

沿用目标项目的 API/schema 权威定义和生成流程。不要直接改生成文件，也不要预设语言、数据库、路由前缀或代理架构。字段定义保留单一事实来源，计划引用规格，避免两份字段表漂移。

未完成依赖如需桩，应明确不可用并关联消除任务，不得伪造成功。真实接线、错误传播和最终副作用需纳入最终验收；跳过的集成测试不算通过。

## 交付边界

仅要求规划时交付规格或计划，不自动开始实现。已授权实现时按依赖推进，遵循用户或项目明确的审查节点，不自行追加每个任务都等待批准的流程。更新完成状态时以实际验证为准，最终检查孤立桩、失效 TODO 和尚未接通的真实路径。
