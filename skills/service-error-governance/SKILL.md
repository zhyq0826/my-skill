# 服务错误与日志治理

## 先确定观测责任

跟踪一个失败从发生点到最终调用方的路径，确认 HTTP/RPC 边界、任务执行器或消息消费者是否统一记录错误。只有已证实上层会记录，才能删除下层重复日志；不能把“返回错误就不打日志”当成所有服务的默认规则。

## 错误传播与对外映射

- 返回链保留根因、错误类型和已有业务码，按目标项目封装方式补充操作与对象语境。Go 包装需保留 errors.Is/As 可判定性，不能用字符串比较替代稳定契约。
- 外部服务错误在集成边界映射；内部已分类的业务错误避免被再次包装成无差别系统错误。用户可见文案与内部诊断信息分开处理。
- 检查被丢弃的包装返回值、误返回 nil、变量遮蔽，以及 named return/defer 修改最终错误等问题。成功路径不能携带旧错误。
- 同一失败在既定责任边界记录一次；中间事件只有提供独立业务意义时才单独记录，不机械禁止所有中间日志。

## 非返回链路

旁路任务、goroutine、定时任务和消息消费没有正常调用栈兜底时，明确失败由谁记录和处理。保留必要关联 ID 与操作上下文，不把完整请求或敏感载荷直接打入日志。

消息解码失败、未知类型和业务失败需结合框架确认 ACK、重试、死信或明确丢弃的语义。不能为减少报错直接返回成功，也不能让永久错误无限重试。取消、超时与重复消息应按实际业务策略处理。

## 验证

验证返回错误的类型/码、边界映射、重试或确认行为及关键副作用。日志治理关注责任边界是否漏记或重复，不为每条措辞写脆弱测试。使用目标项目的错误库、结构化日志和测试命令，不引入新的统一框架作为治理前提。
