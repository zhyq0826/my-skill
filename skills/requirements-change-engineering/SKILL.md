# 需求变更工程

## 先把变化说清

用短简报说明旧行为、新行为、变更原因和受影响对象。区分契约变化、同名字段的语义变化、校验与默认值变化、功能范围扩展；多种类型可同时存在。

按实际消费者、流量和存量数据判断风险。未上线功能也可能被其他团队或共享接口依赖；已经上线也不意味着每次都要双写或版本化。

## 沿链路检查影响

基于代码定位受影响层及文件，注明已确认、待确认或不适用，避免仅凭字段搜索推断完整影响面：

| 层面 | 容易遗漏的内容 |
| --- | --- |
| 契约与领域模型 | 字段类型、可选性、枚举含义、单位、序列化标签、生成代码 |
| 存储与查询 | 插入和更新路径、旧数据缺失值、索引、缓存、历史数据语义 |
| 业务与调用方 | 校验、默认值、聚合与字段透传、事件消费者、旧客户端 |
| 前端 | 新建表单、编辑回填、提交 payload、预览与列表、权限 |
| 配套 | 本地化、测试夹具、初始化脚本、文档与验收标准 |

必要的前端、测试、初始化数据和契约文档不能机械降为后续事项；以能否正确交付新行为判断。

## 选择落地策略

无存量且无外部依赖时可直接统一契约和实现。涉及存量时，明确旧格式读取、新格式写入、迁移幂等性及失败恢复。按需要选择兼容读取、分阶段迁移、双写或接口版本化，并写清过渡状态的退出条件。

同名字段改含义尤其要检查旧数据是否还能区分；回滚代码不能自动撤销数据迁移，须说明数据回退或继续兼容的方式。实际生产迁移与发布遵循用户授权范围。

## 完成标准

从权威契约修改并生成派生产物，沿真实读写链路验证。测试优先覆盖新行为、受影响的旧输入、历史缺值及失败恢复；同步失效文档和任务状态。汇报变更结果、兼容处理、验证证据及仍存在的依赖，不把整张矩阵当成固定的冗长输出模板。
