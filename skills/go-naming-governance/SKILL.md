# Go 命名治理

## 确定范围

先读目标项目命名约定及本次 diff，优先处理新增代码和相关调用链。纯历史命名债单列，不把局部治理扩展成全仓改名。

## 识别与改名

- 根据值的业务角色命名，区分实体、快照、请求、响应、索引、数量和标识符；不要把不同概念统一叫 data 或 result。
- 优先消除单字母业务别名、无约定的截断、拼音首字母，以及同一概念多种叫法。先看类型和用途，不能仅凭正则命中就认定错误。
- 保留语境明确的 Go 惯例，如 ctx、err、ok、短循环 i/j、HTTP handler 的 w/r，以及目标项目已认可的缩写。简短 receiver 不应仅因长度被机械展开。
- 新名称说明业务语义，但避免重复包名和类型已经提供的信息。先确定术语，再沿实际引用修改。

## 保持契约与验证

局部重命名不能顺带改变 JSON/BSON 标签、数据库字段、协议字段、日志分析依赖的字段或公开 API。导出符号、反射及按名称注册的入口需检查消费者。生成代码应改源定义并使用已有生成流程，不手改产物。

采用符号级重命名或逐处确认，避免全文字符串替换误改注释、协议与无关变量。格式化后检查 diff，运行相关包编译及必要测试；报告实际范围、契约是否受影响及验证结果，不凭纯命名宣称没有回归风险。
